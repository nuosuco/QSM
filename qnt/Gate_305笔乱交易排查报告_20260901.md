## 二、根因查明

### 2.1 Gate 305笔交易的真实来源

**详细统计**：
```
总交易数: 305笔
总金额<3U: 271笔 (88.9%)
总金额>=3U: 34笔 (11.1%)
```

**按日期分布**：
| 日期 | 总交易 | <3U | >=3U | 币种 |
|------|--------|-----|------|------|
| 8/29 | 50笔 | 45笔 | 5笔 | OP, DOT, ATOM, TIA |
| 8/30 | 17笔 | 17笔 | 0笔 | ARB, OP, FET |
| 8/31 | 220笔 | 199笔 | 21笔 | 12种币种 |
| 9/1 | 18笔 | 10笔 | 8笔 | ARB, OP, ATOM, TIA |

**关键发现**：
- **92.5%的交易金额<3U**，完全不符合当前Gate最小订单规则
- **时间特征**：UTC 06:00-09:00密集交易，每3-5分钟一笔
- **规律性极强**：同一order ID在多笔交易中重复出现（说明是程序化交易）

### 2.2 交易来源分析

**时间线对比**：
- 8/28 21:22: engine首次连接Gate，报错"USER_NOT_FOUND"（期货账户未开通）
- 8/29 06:46: 第一笔交易开始（UTC时间）
- 8/30-8/31: 大量交易持续发生

**推测来源**：
1. **旧版engine代码**：可能存在不同的阈值配置，允许更低金额交易
2. **其他脚本/手动交易**：未记录的独立交易脚本
3. **API密钥复用**：使用了与engine相同的API密钥

**排除的可能**：
- ❌ agent_exchange目录：代码仅用于TODO框架，无实际交易逻辑
- ❌ qnt_heartbeat.py：纯监控脚本，无交易功能
- ❌ qnt_auto_monitor.py：仅监控，无下单逻辑

### 2.3 为什么engine_trades没有记录？

**最可能的原因**：
1. 这些交易发生在当前engine代码部署之前
2. 旧版代码可能成功下单，但日志记录不完整
3. 使用了不同的代码版本或分支

**证据**：
- Git历史显示8/17是"QNT v0.0.1稳定版"
- 8/29的交易可能是那个版本产生的
- 后续版本逐步收紧了风控规则

## 三、风控漏洞修复

### 3.1 已完成的修复

#### 修复1: config.py - 安全默认值
```python
# 修复前（危险）
enabled: bool = True

# 修复后（安全）
enabled: bool = False  # 必须手动开启实盘
```

#### 修复2: execution_engine.py - 严格价差检查
```python
# 三层检查，确保价差>0.17%才能交易
if spread_pct < self.BI_SIDE_COST * 100 + RiskManager.MIN_NET_PROFIT_PCT:
    continue  # 价差不足成本线+净利要求，跳过
```

#### 修复3: dual_engine.py - 回测/模拟严格风控
```python
# 回测和模拟也加入相同的严格检查
if spread_pct < ExecutionEngine.BI_SIDE_COST * 100 + RiskManager.MIN_NET_PROFIT_PCT:
    return
```

#### 修复4: risk_manager.py - 净利润阈值
```python
# 用户要求：净利=0.01%，成本=0.16%，价差=0.17%
MIN_NET_PROFIT_PCT = 0.01  # 定死不变
```

### 3.2 风控规则（定死）

**成本线**：0.16%（双边手续费+滑点）

**交易门槛**：
- 价差必须 > 0.17% 才能交易
- 净利必须 > 0.01% 才能交易
- Gate最小订单：≥ 3U
- 币数量精度：≥ 1个

**仓位管理**：
- 单笔仓位 ≤ 总资金 20%
- 止损 ≤ 总资金 2%
- 连续亏损 3 次暂停
- 最大回撤 30% 停止

## 六、教训总结

### 6.1 技术教训

1. **安全默认值**：所有开关默认必须为False
2. **硬编码检查**：不能只依赖配置，代码中必须有硬编码检查
3. **数据库写入**：所有交易必须写入数据库，失败也要记录
4. **回测真实性**：回测必须模拟真实约束条件
5. **日志完整性**：确保所有路径都有日志输出

### 6.2 流程教训

1. 修改代码后必须测试验证
2. 上线前必须code review
3. 重要变更必须备份原代码
4. 实时监控日志，发现问题立即停止

### 6.3 风控教训

1. **阈值不能反复修改**：每次修改都要有充分理由
2. **最小订单必须遵守**：交易所规则不可突破
3. **成本计算要准确**：0.16%是硬性成本线
4. **净利要求要明确**：用户要求>0.01%是底线
