# SOM 松麦 - 项目总方案

> 有机认证 · 药食同源 · 健康环保 · 中医养生

## 项目概述

**项目名称：** SOM（松麦）  
**域名：** som.top  
**助手名称：** 小麦SOM  
**定位：** 中医辨证 + 有机认证药食同源 + 游戏化养生的健康生活平台

**核心理念：**
- 不卖货，卖"对症的养生方案"
- 不教课，让用户在玩中学会养生
- 不强调技术，用户感受到的是一个懂你的养生伙伴

**产品标准：**
- 只做有机认证的有机食品
- 只做药食同源食材（有正规资质）
- 只做健康环保认证的健康产品
- 不做无资质证明的"原生态"产品

## 技术架构

### 核心引擎

```
小麦SOM = 云端LLM（商汤/Agnes）+ RAG知识库 + 规则辨证引擎
```

- **云端LLM**：商汤SenseNova 6.7 Flash-Lite（主力，支持图片输入）+ Agnes 2.0 Flash（备用），全免费额度
- **RAG知识库**：中医辨证逻辑 + 药食同源食材库 + 体质辨识体系 + 食疗方案
- **规则辨证引擎**：症状→证型→体质判定，可控可审计，不依赖LLM
- 所有功能模块共享同一引擎和知识库

### 技术栈

| 层级 | 技术选型 | 说明 |
|------|---------|------|
| 前端-微信小程序 | 原生小程序框架 | 微信生态，用户基数大 |
| 前端-网页版 | Vue 3 / React | som.top，与小程序功能同步 |
| 后端服务 | Node.js / Python FastAPI | 统一API，同时服务小程序和网页 |
| 模型推理 | 云端API（商汤/Agnes）+ 本地Ollama备用 | 免费额度优先，数据自主 |
| 知识库 | RAG（关键词检索 + JSON知识库） | 中医辨证 + 药食同源 |
| 数据库 | SQLite / PostgreSQL | 用户数据、对话记录、积分系统 |
| 商品对接 | 淘宝联盟API + 京东联盟API + 拼多多联盟API | 三平台佣金 |

### 部署方案

**第一阶段（当前服务器）：**
- 服务器：2核CPU / 8GB内存 / 无GPU
- 模型走云端API（商汤SenseNova + Agnes AI，全免费额度）
- 本地Ollama已装好备用，MVP阶段不启用
- 足够支撑前期用户

**第二阶段（用户量增长后）：**
- 升级服务器或租用GPU实例
- 部署更大模型（7B级别中医专用模型）
- 知识库持续扩充

## RAG知识库核心内容

### 药食同源食材库

基于国家卫健委公布的药食同源目录，包含：
- 食材名称、性味归经
- 功效与适应症
- 禁忌与注意事项
- 常见搭配（配伍）
- 推荐食谱

### 体质辨识体系

基于中医九种体质分类：
- 平和质、气虚质、阳虚质、阴虚质
- 痰湿质、湿热质、血瘀质、气郁质、特禀质
- 每种体质的特征、易患疾病、调养原则

### 辨证逻辑规则

- 症状 → 证型 的映射规则
- 多症状组合的辨证逻辑
- 证型 → 食疗方案 的推荐规则
- 特殊人群（孕妇、儿童、老人）的禁忌规则

## 差异化护城河（2026-07-28 补充）

### 核心判断：别在体验上跟淘宝刚，要在专业度上让淘宝够不着

跳转淘宝体验不好是所有导购平台的通病（小红书、什么值得买都跳），用户早习惯了。真正决定生死的不是"跳转那一下"，而是**用户有没有非来不可的理由**。

**SOM 的不可替代性（淘宝给不了的）：**

| 维度 | 淘宝 | SOM |
|------|------|-----|
| 商品组织 | 按品类堆（搜"有机小米"） | 按养生方案配（"气虚补气套餐""祛湿食谱"） |
| 决策依据 | 销量/价格/评价 | 体质测评 + 辨证结果（你是气虚质，该吃这个别碰那个） |
| 内容信任 | 商家自卖自夸 | 药食同源知识库 + 辨证逻辑，专业背书 |
| 用户画像 | 购买偏好 | 体质画像 + 证型 + 养生阶段 |

**一句话：淘宝卖货，SOM 卖"对症的养生方案"。货只是方案的载体。**

### 三层数据壁垒（越用越深，抄不走）

```
体质测评数据 → 辨证记录 → 养生方案效果反馈
        ↓
知识库越喂越准 → 辨证越准 → 用户越信 → 数据越多
        ↓
这是复利，不是功能，别人复刻不了
```

### 推广策略（冷启动）

中医养生是高度垂直的圈子，别想着大众投放，走精准口子：

1. **内容种草** — 公众号/小红书发"九种体质自测""节气食疗"，文末引流到测评
2. **社群渗透** — 中医养生群、宝妈群、亚健康白领群，体质测评是天然钩子
3. **测评裂变** — "测测你是什么体质"结果可分享，带二维码
4. **信任前置** — 先让用户觉得"这儿辨证准"，再谈买东西。别一上来就卖货

**关键：登录时机往后推。** 让用户先玩起来→做完体质测评→最想保存结果时→弹"登录后永久保存+多端同步"。转化率最高。

## som.skill 平台化架构（2026-07-28 补充）

### 终极形态：SOM 不是一个 App，是一套"养生能力 API"

把后端沉淀成 `som.skill`，供购物助手、各端小程序、第三方调用。前端（网页/小程序）只是这套能力的**一个**消费方。

```
┌─────────────────────────────────────────┐
│           som.skill（养生能力层）           │
│  · 体质测评 API    · 辨证引擎 API           │
│  · 药食同源知识库   · 食疗方案生成           │
│  · 有机商品搜索     · 用户/积分系统          │
└───────────────┬─────────────────────────┘
                │ 统一 RESTful API
    ┌───────────┼───────────┬──────────────┐
    ↓           ↓           ↓              ↓
 网页版      微信小程序    购物助手      第三方接入
(som.top)   (原生)      (各AI助手)    (开放平台)
```

### 设计原则

- **API 先行**：所有能力先有干净的 REST 接口，前端只是调用方
- **能力解耦**：辨证、测评、商品、用户各自独立模块，可单独调用
- **多端复用**：网页和小程序共用同一套后端，不重复造轮子
- **开放预留**：API 设计时就考虑第三方调用（鉴权、限流、版本）

### 当前后端已具备的能力（可直接 skill 化）

| 能力 | 接口 | 状态 |
|------|------|------|
| 中医辨证 | `/api/chat` | ✅ 规则引擎已跑 |
| 商品搜索 | `/api/products/search` | ✅ 实时并行搜索 |
| 药食同源库 | `/api/knowledge/yaoshi` | ✅ |

## 技术决策记录（2026-07-28）

### 商品缓存（23747条）：保留，降级用途

- 主搜索走**实时**（淘宝联盟并行），缓存不在主链路
- 缓存降级为：**商品详情富化层**（补详情图/参数/描述）+ **实时接口兜底**
- 抽查3000条仅3.6%是单图，"只有一张图"非主要问题
- **不删除**

### Ollama / 本地模型：MVP 阶段不启用

- 基础设施已就绪（Ollama v0.30.10，服务 active），但**未装任何模型**
- 服务器 2核8G **无GPU**，2B模型跑CPU慢
- MVP 辨证用**规则引擎+RAG**，比小模型更准更可控
- Ollama 保留，第二期做自然语言交互/som.skill 智能层时再拉模型

### 单页应用：长期可行，不换多页

- SPA 无天花板，关键在架构（路由规范化 + 模块化 + 数据上后端）
- 真正瓶颈是数据持久化（localStorage 换设备丢），已用后端数据库解决
