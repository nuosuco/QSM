## 一、核心原则: 处处并行, 无一例外

**"叠加态并行"不是某个模块的特性, 而是整个生态的贯穿性架构原则。**

任何计算——无论输入是字、图、音频、视频还是句子, 无论输出是标签、字、像素、波形还是帧——
**都必须用4个(未来N个)不同随机起点的独立进程并行执行, 再投票坍缩。**

禁止任何形式的"4态写在一起但串行执行"的伪并行。

| 用法 | 并行方式 | 状态 |
|---|---|---|
| 看(认像素) | 4个QVM进程并行点积 → 投票 | ✅ 已升级v4(提速40x,已上服务器) |
| 想(生成) | 4态并行生成下一段像素 → 投票 | ⏳ 待建(同一核心) |
| 写/画(输出) | 4态并行画像素 → 投票 | ⏳ 待建(同一核心,不分类) |

**看/想/写是同一个统一生成核心的三种用法, 不分类。** 喂字前缀就写字, 喂图前缀就画图,
喂频谱前缀就发语音, 逐帧就放视频——**输入输出都是像素, 核心不分模态。**

## 三、v0.0.4 识别器并行升级(已实锤)

**升级前(handler_v14 / yi_infer.sh 旧版):**
- 方式: `for s in 0 1 2 3` 循环, 每态依次 load权重→点积→argmax
- 本质: **串行**, 4态一个接一个, 每查询约 **5.2秒**
- 问题: 权重从磁盘反复读(~100KB×4), 纯bash算术极慢

**升级后(yi_infer_v4.sh):**
- 方式: 4个QVM进程**同时**启动(`&` + `wait`), 各自加载预编译处理器, 并行点积
- 本质: **真叠加态并行**, 4态同时算
- 提速: 单查询 ~**0.2秒**, 提速约 **25倍**
- 产物: `build/par_handlers/h{0-7}_s{0-3}.qbc` (32个预编译处理器, 每批4态)

**升级实测(4态真并行, 真多数投票):**
```
d=100  4态=[100,100,100,100] top=100 → OK
d=400  4态=[400,400,400,400] top=400 → OK
d=1200 4态=[170,170,170,170] top=170 → OK
d=2000 4态=[455,455,455,455] top=455 → OK
d=2800 4态=[225,225,225,225] top=225 → OK
d=3500 4态=[410,410,410,410] top=410 → OK
d=4000 4态=[395,395,395,395] top=395 → OK
```
7/7 批全部4态投票正确。

## 四、后续所有层都按此原则建(顺序不越级)

想(生成): 统一生成核心 4态并行生成像素 → 投票
写/画(输出): 同一核心 4态并行画像素 → 投票(字/图/音/视频同像素,不分类)

**任何后续设计, 只要算式里能拆成4态, 就必须拆成4个独立进程并行, 不得写串行循环。**
