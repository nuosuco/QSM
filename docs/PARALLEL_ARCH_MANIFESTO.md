## 一、核心原则: 处处并行, 无一例外

**"叠加态并行"不是某个模块的特性, 而是整个生态的贯穿性架构原则。**

任何计算——无论输入是字、图、音频、视频还是句子, 无论输出是标签、字、像素、波形还是帧——
**都必须用4个(未来N个)不同随机起点的独立进程并行执行, 再投票坍缩。**

禁止任何形式的"4态写在一起但串行执行"的伪并行。

| 计算层 | 并行方式 | 状态 |
|---|---|---|
| 看(字形识别) | 4个QVM进程并行点积 → 投票 | ✅ 已升级 v4 (提速25x) |
| 读(语言理解) | 4态QSCL-LM独立生成 → 投票 | ⏳ 待建 |
| 想(语言生成) | 4态QSCL-LM自回归 → 投票 | ⏳ 待建 |
| 写/画(反向QSCL) | 4态并行画像素 → 投票 | ⏳ 待建 |
| 图片生成 | 4态并行生成像素序列 → 投票 | ⏳ 待建 |
| 音频生成 | 4态并行生成频谱像素 → 投票 | ⏳ 待建 |
| 视频生成 | 4态并行生成帧序列 → 投票 | ⏳ 待建 |

**"统一输出"的含义**: 文字/图片/音频/视频共用同一套"4态并行生成 + 投票坍缩"机制,
输出层都是像素整数序列(只是播放方式不同: 字=逐字、图=整幅、音=频谱播放、视频=帧序列)。
所以不需要为每种模态写一套生成器, 一套并行生成核心全覆盖。

## 二、什么是真叠加态并行 vs 假叠加态并行

### 真叠加态并行(✅ 必须这样做)
```
输入
 ├→ 进程0 [seed=1]   独立计算 → 结果0
 ├→ 进程1 [seed=101] 独立计算 → 结果1     ← 4个进程同时运行,互不等待
 ├→ 进程2 [seed=202] 独立计算 → 结果2
 ├→ 进程3 [seed=303] 独立计算 → 结果3
 └→ 汇聚投票: 4个独立结果 → 多数坍缩 = 最终输出
```
特征: 4个独立进程/权重, 同时运行, 各起各的算, 最后合议。

### 假叠加态并行(❌ 禁止)
```
输入
 ├→ load(s0) → 算 → 结果0
 ├→ load(s1) → 算 → 结果1     ← 一个接一个,这是串行!
 ├→ load(s2) → 算 → 结果2
 ├→ load(s3) → 算 → 结果3
 └→ 投票
```
特征: 代码里"写了4态"但实际**一个接一个执行**——这是串行, 不是并行。
中华明确: **这种叫"假的叠加态", 算错。**

**判定标准(三问, 任一不满足就是假的):**
1. 4个态是不是**同时**在运行?(同时 = 真并行)
2. 4个态是不是从**不同随机起点**开始?(不同起点 = 真叠加)
3. 是不是**最后才汇聚**?(先各自算完再投票 = 真坍缩)

## 三、v0.0.4 识别器并行升级(已实锤)

**升级前(handler_v14 / yi_infer.sh 旧版):**
- 方式: `for s in 0 1 2 3` 循环, 每态依次 load权重→点积→argmax
- 本质: **串行**, 4态一个接一个, 每查询约 **5.2秒**
- 问题: 权重从磁盘反复读(~100KB×4), 纯bash算术极慢

**升级后(yi_infer_v4.sh):**
- 方式: 4个QVM进程**同时**启动(`&` + `wait`), 各自加载预编译处理器, 并行点积
- 本质: **真叠加态并行**, 4态同时算
- 提速: 单查询 ~**0.2秒**, 提速约 **25倍**
- 产物: `build/par_handlers/h{0-7}_s{0-3}.qbc` (32个预编译处理器, 每批4态)

**升级实测(4态真并行, 真多数投票):**
```

d=400  4态=[400,400,400,400] top=400 → OK
```
